# 旧 Axure 原型规律

Use this reference when generating Axure-style HTML prototypes from Chinese product requirements or old prototype examples. These patterns come from a large Axure HTML export with `boss_pc` and `boss_app` page families.

## 1. Overall Style

- Treat the prototype as a business document, not only a UI mockup.
- Keep real UI and reviewer notes separate.
- Preserve old-version traces when they affect scope: version notes, `待开发`, `作废`, `新增`, `修改`, and red change text should become yellow reviewer notes unless users should actually see them.
- Page titles often include version numbers. Keep the business page name readable and move version/change history into notes.
- Use concrete sample data in lists and details so reviewers can understand row actions.

## 2. PC Backend Patterns

Common PC pages:

- **Business center/list page**: left navigation, top bar, filter/search area, table, pagination, row actions.
- **Detail page**: title, close/back, grouped field sections, operation buttons, related records, notes.
- **Create/edit form**: grouped required fields, dropdowns, switches, validation notes, save/cancel.
- **Approval detail**: approval title, approval timeline, current status, applicant data, approve/reject buttons, print/download when needed.
- **Report/statistics page**: date/company/school filters, wide table, formulas, export, pagination, data range notes.
- **Configuration/metadata page**: list plus add/edit/enable/disable/delete actions, status column, operation restrictions.
- **Import/export page**: upload/import result, failed records, export button, error explanation.

PC layout conventions:

- Left navigation shows business hierarchy, not page states.
- Top area identifies current system/module and user/account entry.
- Filter area appears before table data.
- Table rows need enough key fields for row operations.
- Row actions such as view, edit, approve, reject, enable, disable, delete, confirm, print, and export need explicit results.
- Long formulas, permission rules, and data-source rules belong in yellow notes.

## 3. Mobile App Patterns

Common App pages:

- **Phone shell**: device frame, status bar, title/nav bar, content area.
- **List page**: cards or rows, search/filter entry, empty state, item click to detail.
- **Detail page**: grouped fields, status, related records, footer actions.
- **Form page**: required fields, picker/dropdown, input validation, save/cancel.
- **Confirmation/signature page**: summary data, confirmation copy, signature/confirm button, result state.
- **Personal center/page group**: account info, password/avatar/message/detail entries.

Mobile layout conventions:

- Keep screen content inside the phone frame.
- Put annotations outside the phone frame.
- Show default state in the phone UI; put alternate states in yellow notes unless the task requires multiple screen previews.
- App and PC versions can have different scope, fields, and action results.

## 4. Yellow Requirement Notes

Use right-side yellow notes for:

- Page purpose and business background.
- Field source, display rule, edit rule, validation rule, and required/optional state.
- Button trigger, click result, jump target, popup content, confirm/cancel behavior, disabled/hidden condition.
- Permission scope: group, company, school, department, personal, role, ownership, or row-level authority.
- Data range and data source visible to business reviewers.
- Status definitions, before/after transitions, approval stages, reject reason behavior.
- Formulas and report-calculation rules.
- Version changes and old-data handling.
- Pending questions and assumptions.

Do not place reviewer-only notes inside the PC or phone wireframe. If the old prototype used red text as explanation, convert it to a yellow note.

## 5. Page Content Rules

For each page, define:

- Page name and side: PC, App, or both.
- Page purpose.
- User-visible sections.
- Fields and sample values.
- Buttons and actions.
- Default state.
- Empty/exception/no-permission states.
- Popup or child page ownership.
- Yellow notes.

Only confirmed user-visible content enters the wireframe. Internal business rules, backend logic, calculation rules, and pending items go to notes.

## 6. Buttons, Row Actions, and Popups

Every button needs a result:

- Jump to page.
- Open business popup.
- Save and refresh.
- Return/close.
- Change status.
- Disable/hide based on status or permission.
- Pending result marked as `按钮结果待确认`.

For row actions:

- Identify the selected row object.
- Carry key row fields into the popup or target page, such as name, contact, amount, product, status, school, owner, or time.
- Define confirm result and cancel result.

Business popup minimum content:

- Title.
- Selected object summary.
- Required input fields if any.
- Action explanation when needed.
- Cancel button.
- Confirm button.
- Confirm result.
- Cancel result.

Avoid generic confirmations such as "是否确认操作" without selected object and result.

## 7. State and Approval Patterns

State notes should cover:

- Default state.
- Empty state.
- Loading/error/no-permission when relevant.
- Waiting review, approved, rejected, cancelled, completed, disabled, enabled, failed, imported-failed, or expired states.
- Before/after status for each state-changing action.

Approval pages should show:

- Applicant/request summary.
- Approval flow or timeline.
- Current approval status.
- Approve/reject actions.
- Required reject reason or approval note.
- Result after confirmation.

Do not put states in navigation. Put them under the owning page.

## 8. Common Quality Problems to Prevent

- Page names exist but content is missing.
- Navigation is inferred only from file names.
- Fields and buttons are mixed together.
- Business rules are drawn as fake UI modules.
- Row actions open generic popups without selected-row data.
- Buttons have no click result.
- Red text or reviewer notes appear inside the phone/PC wireframe.
- PC and App are assumed identical without evidence.
- Version changes are dropped.
- Pending questions are silently decided.

## 9. Final Review Checklist

- Page hierarchy exists before page drawing.
- Every page has visible content.
- Every field has source or pending marker.
- Every button has result or pending marker.
- Every popup has title, selected object, content, confirm result, and cancel result.
- Every state belongs to a page.
- Every important rule appears in yellow notes.
- User-visible UI is separated from reviewer notes.
- PC/App differences are explicit.
- The HTML prototype can be clicked through for review.
