# 原型反馈到需求与原型闭环

Use this reference when the user reviews a prototype and points out that something is wrong, missing, misplaced, unclear, or should be adjusted. The goal is to decide whether the feedback only changes the prototype surface or must also update requirement analysis and prototype-design input.

## 1. Core Rule

Do not directly edit the prototype before classifying the feedback.

Every feedback item must be routed to one of these sinks:

- Requirement analysis update.
- Prototype-design input update.
- HTML/prototype UI update.
- Yellow note update.
- Pending question.
- No requirement impact, prototype-only adjustment.

If a feedback item changes business meaning, data, action result, status, permission, or navigation, it must feed back into the requirement document. Do not leave the change only in HTML.

## 2. Feedback Classification

| Feedback type | Typical user wording | Requirement impact | Prototype impact |
|---|---|---|---|
| Business rule | 这里规则不对、这个条件下不能展示、这个状态应该允许操作 | Update 业务规则 and related sections | Update yellow notes and affected UI/states |
| Field | 这个字段不要、这里少一个字段、字段来源不对 | Update 字段说明 and page content | Add/remove/change field in UI or notes |
| Button/action | 这个按钮点错了、按钮结果不对、这里应该弹窗 | Update 功能按钮与操作说明 and 页面跳转逻辑 | Update click behavior, popup, notes |
| Page structure | 这里应该拆成两个页面、这个页面不该放这里 | Update 页面内容说明 and 页面层级树 | Update navigation, pages, entry relationships |
| Transition | 点这里应该去详情页、返回路径不对 | Update 页面与跳转逻辑 | Update clickable links/hash/script |
| Popup | 弹窗内容不对、确认后状态不对、取消不应该刷新 | Update button result and popup content | Update popup UI and confirm/cancel behavior |
| State | 缺空状态、驳回后怎么显示、审核中按钮置灰 | Update business/state rules | Update page state notes or state preview |
| Permission | 这个角色不能看、校区只能看本校区 | Update 业务规则, 字段规则, PC/移动差异 | Update visible/hidden/disabled rules in notes/UI |
| Yellow note | 说明不完整、这里需要写清楚规则 | Usually update relevant requirement section if rule is new | Update yellow notes |
| Visible wording | 页面文案改一下、按钮叫提交审核 | Update requirement only if wording changes business meaning | Update UI text |
| Pure visual | 间距太挤、颜色太重、按钮放右上角 | No requirement impact by default | Update UI layout/style only |

When a single comment contains multiple issues, split it into separate feedback items before routing.

## 3. Requirement Feedback Rules

Update requirement analysis when feedback affects:

- Conditions, eligibility, restrictions, or business results.
- Field existence, source, visibility, editability, validation, or flow.
- Button trigger, result, target page, popup, save/refresh/return behavior, or display condition.
- Row-action selected object and selected-row fields.
- Status names, before/after status, approval/reject behavior, reason requirements, or user-facing result.
- Permission scope across group, company, school, department, personal, role, or ownership.
- PC/mobile scope or differences.
- Page hierarchy, page ownership, entry path, or navigation.
- Pending questions becoming confirmed answers.

When updating the requirement analysis, update all affected sections, not only the obvious one:

- Business rule feedback may also affect fields, buttons, page content, states, and prototype-design input.
- Field feedback may affect button rules, page content, permissions, and PC/mobile differences.
- Button feedback may require adding target page content or popup content.
- State feedback may require changing button display rules and yellow notes.

## 4. Prototype Feedback Rules

Update prototype output when feedback affects:

- Page layout, visible content, or visual hierarchy.
- Navigation, clickable links, tabs, anchors, or page switching.
- Popup UI, confirm/cancel buttons, selected object summary, or result text.
- Right-side yellow note content.
- Default, empty, exception, disabled, or no-permission state presentation.
- PC/mobile rendering differences.

Prototype-only changes are allowed when feedback is clearly visual or wording-only and does not change business meaning. Still record that the requirement document is unaffected.

## 5. Change Record Format

For each feedback round, produce a compact change record unless the user requests a clean final-only output.

```markdown
## 本轮反馈处理记录

| 反馈 | 分类 | 需求文档影响 | 原型影响 | 处理结果 | 待确认 |
|---|---|---|---|---|---|
| 提现按钮应进入提现详情，不是弹窗 | 按钮/跳转 | 更新功能按钮与操作说明、页面与跳转逻辑 | 更新提现列表点击行为和详情页入口 | 已调整 | 无 |
```

Use `无` only when there is truly no pending point. If uncertain, write the exact question.

## 6. Typical Handling Examples

### Example A: Button target is wrong

Feedback: `这里的查看按钮应该进入订单详情，不是打开弹窗。`

Handle as:

- Classification: button/action + transition.
- Requirement update: update 功能按钮与操作说明 and 页面与跳转逻辑.
- Prototype update: change click target to order detail page; ensure detail page exists and has content.
- Change record: note affected page and target page.

### Example B: Field should not be visible

Feedback: `用户端不要展示到账时间，后台可以看到。`

Handle as:

- Classification: field + permission/side difference.
- Requirement update: update 字段说明, PC/移动端差异, 页面内容说明.
- Prototype update: remove field from mobile UI; keep backend UI if in scope; add yellow note.
- Change record: mark requirement and prototype both changed.

### Example C: Rule is wrong

Feedback: `审核驳回后不能重新提交，只能查看原因。`

Handle as:

- Classification: business rule + state + button.
- Requirement update: update 业务规则, 功能按钮与操作说明, state notes, 原型设计输入.
- Prototype update: rejected state hides/disabled submit button and shows reject reason.
- Change record: include before/after status behavior.

### Example D: Page is misplaced

Feedback: `提现详情应该挂在提现中心下面，不应该和首页平级。`

Handle as:

- Classification: page structure.
- Requirement update: update 页面层级树 and 页面与跳转逻辑.
- Prototype update: move navigation node and adjust breadcrumbs/entry.
- Change record: identify old hierarchy and new hierarchy.

### Example E: Pure visual feedback

Feedback: `这个卡片间距太挤，按钮放右上角。`

Handle as:

- Classification: pure visual/layout.
- Requirement update: none by default.
- Prototype update: adjust spacing and button placement.
- Change record: mark `需求文档影响：无，仅原型表现调整`.

### Example F: Yellow note is incomplete

Feedback: `这里要说明分公司只能看本分公司数据。`

Handle as:

- Classification: permission + yellow note.
- Requirement update: update 业务规则 or PC/移动端差异 if not already present.
- Prototype update: add page-level yellow note.
- Change record: mark permission rule added.

## 7. Pending Question Rules

Ask or mark pending when:

- The user says "这里不对" but page/element cannot be located.
- Feedback implies a rule but not the exact condition/result.
- A new button target page is mentioned but target page content is unknown.
- A new popup is required but fields or confirm/cancel results are missing.
- A state changes but before/after status names are unclear.
- PC/mobile scope changes but the affected side is not named.

If the uncertainty does not block the main flow, proceed with a yellow `待确认` note. If it changes the core flow, stop and request the missing business decision.

## 8. Final Checks After Feedback

After applying feedback, verify:

- The feedback was classified.
- Requirement analysis was updated when business meaning changed.
- Prototype-design input reflects the new rules/pages/jumps.
- HTML/prototype UI matches the updated rules.
- Yellow notes explain rules and pending points.
- Related states, popups, row actions, and PC/mobile differences were not left stale.
- The change record is present unless explicitly omitted.
