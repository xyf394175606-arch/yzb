# 专题双副本最终版同步标准

## 背景

项目仓库用于协作、Git 历史和发布，专题外部目录用于向业务方集中交付。两类目录的用途不同，需要统一同步边界，避免外部目录沉淀多个中间版本或与发布版本不一致。

## 目标

- 项目仓库保留完整阶段产物、版本文件和 Git 历史。
- 已登记专题的外部归档目录只保留每类正式交付物的最终版本。
- 所有对话按同一规则创建、更新和清理专题外部归档。

## 输入来源

- 根目录 `AGENTS.md` 的专题登记表。
- 当前任务所属专题、阶段目录和正式交付文件。

## 适用范围

适用于已登记专题的需求分析、业务流程、信息架构、交互设计、数据交互、高保真原型、需求文档和评审记录等正式产物。

不适用于聊天临时截图、系统缓存、下载源文件、草稿、过程文件或未确认材料。

## 专题登记规则

1. 创建新的外部专题归档前，必须先在根目录 `AGENTS.md` 的“专题双副本最终版同步”登记专题名称、外部归档根目录和仓库发布方式。
2. 未登记专题不得擅自同步到外部目录。
3. 外部归档目录沿用项目阶段结构，如 `05_需求分析/`、`10_高保真原型/`、`11_需求文档/`。
4. 专题名称、归档根目录或发布方式变更时，先更新登记表，再同步文件。

## 最终版本判定

“最终版本”指当前经用户确认、可对外评审、交付或发布的最新版正式产物。

- 同一交付物出现多个版本号或多次迭代时，外部目录仅保留当前最终版本。
- 项目仓库可保留不同版本号、修订副本和 Git 提交历史，外部目录不保留这些中间版本。
- 以当前任务已更新的仓库正式文件为同步源；若用户明确指定某个版本为最终版，以用户指定版本为准。
- 同一阶段存在多个不同交付物类型时分别保留，例如 HTML 原型、原型说明和字段复查稿可各保留一份最终版本。

## 同步操作规则

1. 先在项目仓库对应阶段目录完成正式文件创建或修改。
2. 确认文件名符合 `文件主题_调整内容_版本号_创建时间` 规则。
3. 将最终文件复制到已登记专题外部目录的对应阶段目录。
4. 同步前清理外部目录中属于同一交付物类型的旧版本，确保只保留一个最终版本。
5. 对 HTML 原型、Markdown 文档等可校验文件，至少检查外部副本与仓库源文件内容一致；HTML 还需确认可正常解析或打开。
6. 在交付说明中告知用户：外部归档已同步的最终文件范围，以及仓库是否仍承担 GitHub Pages 发布。

## 删除与例外规则

- 删除外部旧版本仅影响专题归档目录，不删除项目仓库历史版本。
- 外部目录已有用户手工文件、非本任务文件或无法准确判断归属的文件时，不得直接删除；先报告并等待确认。
- 用户明确要求保留某个历史版本时，该文件为例外，应在专题归档说明中标明保留原因。
- 发布文件仍以项目仓库副本为准，除非专题登记表明确指定其他发布方式。

## 验收标准

- 已登记专题的外部目录存在对应阶段目录。
- 每类正式交付物在外部目录最多保留一个最终版本，除非存在用户确认的例外。
- 外部最终版本与仓库最终版本内容一致。
- 中间版本仅保留在项目仓库或 Git 历史中。
- 外部目录、项目仓库和发布方式之间的关系可从 `AGENTS.md` 和专题归档说明中追溯。

## 待确认问题

当前无统一待确认项；新专题的外部归档根目录和发布方式须由用户确认后登记。

## 风险与依赖

- 未清理旧外部副本会导致业务方误用过期版本。
- 未同步最新仓库源文件会导致归档副本与发布副本不一致。
- 外部目录不是 Git 替代品，不能承担历史版本追溯。

## 下一步动作

各对话启动时读取本标准。处理已登记专题时，按本标准同步最终版本；处理新专题时，先完成专题登记。
