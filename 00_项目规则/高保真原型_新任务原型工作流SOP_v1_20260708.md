# 高保真原型新任务工作流 SOP

## 背景

本 SOP 用于规范后续新建原型任务的处理顺序，避免每次从聊天记录重新理解流程。适用于 k12 项目中的高保真 HTML 原型、新页面原型、已有原型调整、评审反馈修订和版本更新。

## 目标

- 新任务统一按“需求分析 → 原型结构设计 → HTML 原型制作 → 反馈闭环 → 版本归档”推进。
- 版本更新不默认重开全流程，而是先判断反馈影响环节，再回到对应阶段处理。
- 保证页面层级、弹窗归属、黄色说明区、字段规则和按钮结果在原型中可被评审。

## 输入来源

- `AGENTS.md`
- `00_项目规则/项目总览_工作流程_v1_20260602.md`
- `13_任务卡片/` 中相关任务卡片
- 当前任务相关的上游产物：需求分析、业务流程、信息架构、交互设计、数据交互、旧版原型、截图、评审反馈
- 用户在当前对话中确认的规则和待调整项

## 关键结论

### 1. 任务启动

新建原型任务开始前必须先完成：

1. 读取项目规则、项目总览、相关任务卡片和上游产物。
2. 判断任务类型：
   - 新功能
   - 页面调整
   - 业务规则变更
   - 视觉复刻
   - 评审反馈
   - 版本发布
3. 确认输出目录和文件命名规则。
4. 明确是否基于旧 HTML 原型继续迭代，还是新建版本文件。

### 2. 需求分析阶段

优先使用 `requirement-analysis`。

输出必须覆盖：

- 背景
- 目标
- 已确认需求
- 推测需求
- 待确认问题
- 字段
- 按钮
- 状态
- 权限
- 页面范围

如果输入是截图、旧系统、口头反馈或零散评论，必须先倒推业务规则，不直接进入原型制作。

### 3. 原型结构设计阶段

优先使用 `axure-prototype-design`。

必须明确：

- 页面层级
- PC / 移动端范围
- 导航关系
- 弹窗归属
- 页面入口和出口
- 右侧黄色说明区结构

业务弹窗、抽屉、配置弹窗、评价弹窗、关联弹窗等，只要具有独立字段、规则、按钮结果或状态变化，就必须作为左侧导航节点暴露出来。

弹窗必须挂在所属上级页面下面，左侧导航需要用树形、缩进、分组子节点或父级高亮体现归属，不允许把弹窗与普通页面平铺成同级关系。

### 4. HTML 原型制作阶段

优先使用 `requirements-to-axure-html-prototype`。

原型制作要求：

- 交付可点击 HTML 原型。
- 页面真实 UI 放在中间线框区。
- 字段来源、按钮结果、状态规则、权限、异常、待确认问题放在右侧黄色说明区。
- 所有按钮必须有结果：
  - 跳转
  - 弹窗
  - 保存
  - 刷新
  - 状态变化
  - 禁用说明
  - 待确认标记
- 表格行操作必须能带入当前行的关键字段。
- 弹窗导航节点点击后，应先进入所属页面，再打开对应弹窗。

### 5. 反馈闭环阶段

每条反馈必须先分类，再处理。

| 反馈类型 | 回流环节 | 处理方式 |
|---|---|---|
| 规则、字段、状态、权限变更 | 需求分析 | 更新业务规则、字段说明和黄色说明区 |
| 页面层级、导航、弹窗归属变更 | 信息架构 / 原型结构设计 | 更新左侧导航、页面层级和跳转关系 |
| 表单、按钮、组件交互变更 | 交互设计 | 更新表单规则、按钮结果、组件状态 |
| 接口、字段来源、数据刷新变更 | 数据交互 | 更新接口场景、字段来源、刷新规则 |
| 视觉、文案、布局调整 | 高保真原型 | 直接调整 HTML 原型和可见文案 |
| 评审发现不一致 | 评审记录 | 记录问题，再按影响范围回流 |

修改后必须同步：

- HTML 原型
- 黄色说明区
- 页面层级说明
- 相关按钮结果
- 必要的静态校验

### 6. 版本更新与发布

版本处理规则：

- 小改动：在当前 HTML 上迭代。
- 大改版：按命名规则新建版本文件。
- 需要线上访问时，再同步到 GitHub Pages。

每轮完成后检查：

- 页面可访问。
- 左侧导航层级正确。
- 弹窗归属清楚。
- 黄色说明区同步。
- 无旧口径残留。
- `git diff --check` 通过。

## 待确认问题

- 大改版与小改动的边界是否需要按影响页面数、字段数或评审轮次量化。
- 后续是否需要为“新任务原型启动”单独创建任务卡片模板。
- GitHub Pages 发布是否作为每轮原型调整的默认动作，还是仅在用户明确要求时执行。

## 风险与依赖

- 如果只改 HTML 不同步黄色说明区，评审时容易出现原型与规则不一致。
- 如果业务弹窗未在左侧导航体现归属，后续接手人员难以判断弹窗属于哪个页面。
- 如果版本更新不判断影响环节，可能把需求变更误当作视觉微调处理。
- 多对话协作必须依赖项目文件，不能依赖聊天记忆。

## 下一步动作

1. 后续新建原型任务时，先引用本 SOP。
2. 如任务属于评审反馈，先按反馈类型判断回流环节。
3. 每轮原型完成后，执行导航层级、弹窗归属、黄色说明区和静态校验检查。
4. 如本 SOP 在使用中发现缺口，按版本号新增或更新规则文件。
